# A consistent project document set

Use this when creating a passport and guide together or when the owner requests the full set. Start with the project's existing documents, adapter, environment and source-of-truth map. Reuse canonical equivalents and links; preserve history and access boundaries. The five roles below are reader entry points, not a mandate to duplicate text or create five files. Choose names and output formats to fit the project. For the owner-facing start, prefer this order when the project has no different explicit order: guide, technical passport, agent handoff, recovery, overview.

## Distinct purposes

1. **Product guide:** how the product helps its users, end-to-end scenarios, meaningful rules and known limits. Follow [product-guide.md](product-guide.md); avoid turning it into a test log or setup manual.
2. **Technical passport:** current functions, rules, code/data/integration dependencies, relevant scenarios and verification limits. Keep evidence and change history linked separately.
3. **Agent handoff:** a compact instruction a new agent can actually follow: purpose and authoritative sources; repository and branch or environment when confirmed; first read-only orientation; setup prerequisites; existing scoped checks; how to choose safe test data; present unresolved work and who owns it. Distinguish stable instructions from the dated continuation point and direct the agent to recheck Git state and current sources rather than treat a saved branch or task status as current. Identify explicit authorization boundaries and live-data risks. Link to canonical operational detail rather than copy it. Distinguish a reusable prompt from evidence that it was run, and identify steps requiring human access or secrets without placing secret values in the document.
4. **Recovery guide:** a short, actionable operator entry point for the project's real failure modes, or an explicit statement that recovery is unverified or not applicable. Separately account for relevant code, configuration and secrets, user data and external services; a Git clone or deployment rollback alone is not full data recovery. For each component identify, where known, the authoritative backup/configuration and its owner/location, prerequisites and access path, last evidenced recovery test and limits, isolated verification, ordered recovery/rollback and readback. Where any necessary fact or procedure is missing, say what is unknown, where to stop and what evidence or authorized person is needed next; do not fill in a plausible procedure. Explain how to reach the key independently if encryption is used; do not include secret values. Never claim a backup exists, is current or has been restored solely because a plan or script exists. Never suggest overwriting live state without the project's authorized process.
5. **Project overview:** a short orientation: what it is, for whom, participants, one example, stack, architecture and working links. Follow [project-overview.md](project-overview.md); link the guide/passport rather than reproducing them.

## Consistency and usefulness

- Build a small source map for shared facts: product purpose and status, owner, repository/branch, environment/address, access, deployment, backup/recovery and verification. Check each fact against its current authority; link from other documents instead of keeping competing copies. Clearly separate confirmed, historical, planned, missing and unverified facts. Do not conflate development, local preview and deployed state.
- Trace from a reader question to each entry point and back to actual sources: understand a feature; assess a code change; orient a new agent without inherited context; find what can and cannot be recovered; identify the product quickly. Test links, destination and environment. If paths or documented commands cannot be checked, state the exact gap; do not fill it with assumptions or promise an unverified procedure.
- Provide a navigable index of the five roles, with overview last by default. Reuse existing navigation when suitable; a local Markdown index is enough if there is no UI. Audit any affected start page for duplicate or misleading links without removing useful source documents, breaking existing links, exposing restricted material or changing audience. A restricted entry may need a separate authorized index or a non-sensitive pointer; do not expose private paths or operational details to a broader audience. An existing exact equivalent can supply a role. Arrange a readable view for each only where supported and authorized. A download button is functional only if it really downloads the intended content for the user's access; a link or an inactive mock is not a download.
- When a related fact changes, review only affected roles and their directly shared facts during the same task. For a full-set review, check the whole source map and record revisions/paths, evidence and remaining gaps. If nothing changes in an entry, record a scoped no-change. Do not claim continuous synchronization, deployment or tested recovery from this review alone.
- For an explicit update of the whole project, use the accepted installed skill after its authorized update, inspect current source revisions and working-tree changes, then reconcile all five entries and their shared facts. Update the source documents, refresh applicable generated passport indexes and rebuild existing affected reading views with project commands; verify the index and each configured destination. Do not overwrite authored meaning with generated output or silently approve a new baseline. Identify unavailable commands, stale inputs, unconfigured entries and publication or runtime checks not performed. A copied update prompt starts this agent workflow only when a user gives it to an agent; it is not a scheduler or a background sync.
- Check that the handoff is executable by an agent with only the documented access, and that the recovery entry tells an operator what to do first, where to stop and how to verify. If a project has no server or UI, adapt the relevant sections or mark them not applicable with evidence. An absent or unconfirmed backup is a recovery gap when data or configuration needs preserving, not proof that recovery is inapplicable; do not invent a backup or procedure. For regulated or safety-critical systems retain the owning project's specific obligations and authorized procedures.
