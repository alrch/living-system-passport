# Domain review checks

Use only the checks relevant to the function under review. These prompts capture repeated cross-layer failure modes; they do not replace the project's accepted rule or authorize a broader audit. Search this file for the affected domain (forms, analytics, access, authentication, workflow, integration, files, media, or learning) and inspect its direct neighbors. A detailed example is conditional guidance, not a required feature of every project.

- For field-heavy forms and tables, compare each consequential field across the visible UI, client payload, API validation, service transformation, stored schema, and read/export path. Record defaults and values that silently change between layers. A database field or accepted API value does not prove the UI can set or display it.
- When a service test replaces persistence with a mock, verify consequential enum and required-field paths against the real schema before treating the test as proof of saving. A DTO can accept a value that the database model rejects.
- For analytics and reports, write the metric's numerator, denominator, time window, scope and visible label. Follow separate source counters through aggregation to the actual number, color and export column shown to a person; a correct tooltip cannot repair a misleading primary value.
- For anomaly thresholds based on a cohort or a time window, define the cohort, comparable event, repeat-attempt rule, minimum sample, window boundary, missing telemetry and whether a percentage means relative growth or percentage points. Check whether the event actually carries the grouping key and whether timing or location comes from a trusted source before replacing a simpler heuristic with the stated threshold.
- For an accepted journal or export that promises stable order, compare every role-specific query and merged feed with the exact tie-break key, especially when timestamps are equal. When a page is assembled from limited source queries, sort each source before its limit and use one total order for the merge, including a source discriminator if IDs can collide. Check repeated reads, page boundaries, and output formats; one audience's query ordering does not establish another's ordering.
- For a filterable table with an export, distinguish edited form fields from the applied query. Compare the list, count and download request before and after the user applies a filter; a file can otherwise disagree with the visible evidence even when both API endpoints work correctly. State whether the file covers the current page or all matching rows, and preserve the applied filters when pagination is omitted from a full export.
- For a person filter over several event collections, inspect each collection's stored author ID and email before choosing a key. Do not treat a display name or options from the visible page as a complete identity list. Apply the same identity rule before pagination and count in every source query and export; define how old email-only and unattributed rows appear, and test two people with the same name.
- For a journal or export with a retention deadline, compare the read query with the actual deletion mechanism. State whether a row past its deadline remains visible until cleanup runs, and distinguish the policy deadline from confirmed physical deletion. Check whether list counts, downloads, and direct API responses disclose row limits or truncation; do not describe a capped file as a complete archive.
- For whole-tenant deletion, inventory physical database collections and stored objects independently of models loaded in the current process. Wait for asynchronous model initialization and index creation before dropping collections, then verify the full service path against an isolated database: model registration can recreate empty collections after a seemingly successful drop. Close public and private writes before cleanup, verify a failed step leaves a retryable state, and remove the tenant root only after checking what remains. Trace in-flight requests, background jobs, global audit records and provider-owned data separately; a local success response must describe only the stores it actually verified.
- For background work on a tenant being deleted, check status again after external calls and before each consequential write or message send. A snapshot of approved tenants at the start of a batch does not stop a later job from recreating a dropped collection. Preserve the global job with a clear blocked reason when tenant cleanup interrupts it, so an operator can reconcile outside-system obligations.
- When a table exposes filters as independent controls, verify their intersection in the API query and in the total count. A broad type filter must not overwrite an exact item filter; incompatible selections should produce an empty result rather than silently widening it.
- For optional list or boolean settings with defaults, trace the distinction between an omitted value and an explicit empty or false value through validation, normalization, persistence and readback. Check that every ordinary editor action and preview preserves the loaded value, not only the initial form mapping. A fallback based on truthiness can silently turn a user's deliberate "disable all" choice back on.
- For a new CSV or spreadsheet export, define the source rows and an explicit allowlist of columns before implementation. Compare that allowlist with any JSON export of the same rows, which may serialize additional fields. Exclude stored secrets and internal tokens; check role and tenant scope, row limits, encoding, response headers, escaping, and cells that spreadsheet software could interpret as formulas.
- For a lower-privilege list or detail response, inspect the actual serialized JSON after any shared mapper. Build an explicit field allowlist for that audience; removing one known secret from an object spread can still expose peer identifiers, staff notes, provider metadata, or future schema fields. Keep the consumer's response type aligned with the narrower projection.
- For a date-range filter, compare the UI's input precision and displayed time zone with the server's exact inclusive or exclusive bounds. Test records at the first and last second of the selected minute or day; write down the intended boundary before calling a discrepancy a defect.
- For a selected analytics period, compare the UI's allowed range, API's returned `from/to`, every date or bucket, each aggregation mode and its export. If one view limits older cells for performance while another uses the full period, expose the effective coverage in the contract, visible UI and download description instead of presenting the shorter view as the full period.
- For minimums, maximums and percentages, trace the raw unit through validation, summation, conversion, display rounding and the actual comparison. A displayed rounded value may be useful to read but must not silently decide whether an unrounded value crosses an accepted threshold. If a failing value rounds to the displayed threshold, show the precise shortfall or unrounded source value beside the warning so the visible result remains understandable.
- When an accepted rule blocks publication or another state transition, follow the computed issue into every server path that can reach the target state, including creation with an already open status. Compare the audit label and UI message with the actual reject path; test just below and at the boundary, and confirm the rejected request writes nothing. A visible warning or a passing audit-unit test alone does not enforce the transition.
- For calendar dates and local time rules, identify the canonical time zone for the event and each actor. Compare authoring input, stored instant, server range query, day grouping and viewer display with browsers in different zones, especially across midnight and daylight-saving changes.
- For a limit or one-item action enforced in the UI, inspect every callable API route that can create, update, import, or batch-change the same resource. Check the boundary with a direct request, including values just above the limit and a second unrelated item; a passing form test does not establish the server rule.
- For a submitted answer or attachment, compare the form's nonempty check with the server path before any journal or status write. Test an omitted body, whitespace, empty attachment objects, and each answer mode through a direct request; structural DTO validity does not establish a meaningful submission.
- For a staff decision that publishes a result to another actor, trace every required explanation field from the form through the direct API path before the status or journal write. Test a wholly omitted explanation as well as a partial one; validation only when an optional object happens to be present leaves a bypass.
- For a manual award or certificate action exposed from a group or course screen, test the direct API with an eligible member, an unrelated learner in the same tenant, and a missing prerequisite. The screen context does not restrict arbitrary request IDs; decide whether staff exceptions are allowed and what reason or audit they require before adding a membership guard.
- When a profile field changes through a request and staff decision, compare the self-service PATCH permission list and DTO with the fields the UI submits for review. Verify that the direct route rejects those fields before approval while ordinary contacts still save directly, and that the staff decision can apply the approved values.
- For account recovery, enumerate every public route, including older code-entry screens. Follow each success message to a server-issued token check and changed credential; a client-only code form or resend toast must not present itself as a completed recovery. Preserve role and email context when sending an old route to the current flow.
- For account creation, inspect the actual outgoing message in both self-registration and staff-created flows. Do not repeat a password the user chose in email; a generated initial credential needs a separately reviewed one-time setup or recovery path before the password can be removed from that flow. If a credential is still mailed, escape it for the message format and check that special characters display exactly as intended.
- For a UI action that calls an API, verify the exact HTTP method and path are registered, with the intended role/capability gate, request validation and response contract. A service method or client function alone does not make the visible action usable; a read endpoint that returns individual responses may need a management gate too.
- For a link generated in email or another out-of-band message, follow the actual host, path, query or hash parameters into the page it opens, then trace that page to the matching API route and stored result. If several account types share the page, check token-not-found behavior and old links before changing how the type is selected.
- If an accepted one-item rule conflicts with an older batch route, inspect its known consumers, published contract and tests before changing it. Retire an unsupported batch route together with its contract and tests, then verify that a direct request cannot change a second item; if compatibility is an intended product rule, record that decision instead of silently keeping both behaviors.
- When removing an unused page wrapper, trace its public route and the live replacement first. Preserve compatible redirects and shared components; move tests that read the obsolete source to the actual route and user action so a passing text check does not keep dead code alive.
- When replacing a misleading form with a redirect to another application, preserve old direct URLs, pass only supported context such as role and email, and check each deployment environment's destination. Describe the old route as a redirect in generated inventories and the passport; verify the built server response separately from the receiving application's actual behavior and published availability.
- When replacing emailed initial passwords with invitations, trace every account creation path for the affected roles, including imports and API callers. Keep setup, password reset, and email confirmation tokens separate; check expiry, one-time consumption under concurrent requests, tenant scope, password changes that must revoke an unused invitation, and a recovery path when delivery fails or a link expires. Remove stale password controls and credential copies from the creating UI.
- For workflow entries, trace state transitions and side effects in their actual order: role check, mutation, journal/notification/integration writes, failure, and retry. Explicitly mark a step that can succeed before a later step fails, and distinguish local delivery from external receipt.
- When a resource has a dedicated removal or exclusion workflow with a reason or audit trail, inspect generic update endpoints and legacy client fallbacks for an alternate way to remove the same member or reference. Verify that each callable path preserves the same history or rejects the bypass before writing.
- For autosave, test the dirty interval before the debounce or periodic write as well as the acknowledged draft. Distinguish document unload from browser Back, router navigation, and component unmount; a `beforeunload` warning or `pagehide` flush does not cover every single-page navigation. If navigation is blocked, test both cancel and proceed for browser history and programmatic transitions, then return to verify which draft the server actually acknowledged. A fire-and-forget save on unmount is not proof of preservation.
- For approval, moderation, enrollment, and other competing decisions, check whether two actors can both act on the same prior state. Compare UI button conditions with the server transition predicate, and inspect whether the material change, status update, and audit record are one atomic outcome. Capture a simultaneous-decision and between-writes failure scenario when the sequence permits divergence.
- When a decision publishes or copies a new entity before its event and audit are finalized, replay the same decision after a lost response and concurrently. A conditional status update alone cannot undo an entity already created. Trace each creating branch and its downstream journal, notification, and external send; use a durable event-derived identity or receipt only where replay also preserves those side effects. A short time-window dedupe is insufficient for a delayed replay: test after the window and after a crash between the entity write and each side effect. Mark each branch's evidence separately until the full decision protocol is checked.
- For deferred publication, enumerate every dispatch type saved by writers and compare it with the approval dispatcher. An unknown type must fail the decision visibly; a successful approval with no material action is a broken workflow. Test the actual dispatch for each new type, including any bypass, cancellation, or journal step that applies.
- For account creation, distinguish a unique record ID from a unique login key. If a service checks for an existing email and saves later, inspect the schema, index migrations, and concurrent-create behavior. Preserve intentional shared email across identity providers or tenants when proposing a key. Test both orders of creating local and external identities; an external upsert may allow a shared address while a later local registration rejects it. A scenario that starts with two existing profiles does not prove either creation order. Decide whether the asymmetry is intended before changing either rule.
- When public self-registration and staff creation share a service or DTO, compare their required fields and password ownership separately. Test the public route with omitted and empty fields, then test staff creation without a chosen password; a shared optional schema can silently weaken the public contract.
- In a curriculum audit, distinguish the official hierarchy (module, theme, activity) from the product hierarchy (module, lesson or block). Do not call each lesson a theme merely because an audit projects it that way; compare a real study plan before adding a grouping entity or enforcing every activity within each projected row.
- For a scored learner test, follow stored answer keys through every learner block projection and the result endpoint. Remove choice flags, accepted text variants and matching pairs before an attempt; calculate score and progress from server-held keys, not submitted counts or percent. If review keys are shown after grading, check retry eligibility first so a failed attempt cannot reveal answers for an available retake.
- For outbox and integration flows, compare the locally committed source event with the queue row and external receipt. Check what happens when enqueue fails after the source write, whether a retry encounters an existing event and repairs the missing row, and whether the dispatcher can detect or reconcile gaps. A retryable queue row does not imply every source event reached the queue.
- For scheduled delivery, distinguish content freshness from delivery frequency. At selection time, compare the job's source query with the normal reader's soft-delete and cancellation rules. Check whether a queued message is revalidated when its source event changes or is cancelled, whether consent is rechecked before sending, and whether a report built on demand actually has a scheduler and dated delivery evidence for any promised interval.
- For a new message that discloses sensitive information to another person, identify the exact purpose of consent, who gives it, the verified recipient and any age or relationship condition. Trace grant, refusal, revocation, recipient change and loss of eligibility through the screen, API, stored state and final send decision. An existing consent for a different report or notification is not evidence for this message; keep the internal event when external delivery is suppressed if the accepted workflow requires it.
- For a reminder promised at least N hours before an event, compare the selection horizon with the scheduler interval, the event write path, and actual queue timestamps. Querying only events already within N hours makes every new reminder late; give the scheduler a lead window, handle events created or changed between ticks, test both sides of the cutoff, and label late-created events separately. Trace a platform-channel row through a role-scoped read API into a real screen; a row marked sent is not itself visible to the recipient. Keep platform visibility, email queue creation, and actual email delivery as distinct outcomes.
- For an event reminder that waits in an email queue, change or cancel the event between enqueue and dispatch. Verify the dispatcher checks the current event before SMTP, excludes stale rows from mixed digests, records the skip reason without erasing the row, and schedules the new time separately. Include queued rows created before any new source-reference fields were added.
- For an SMTP retry policy, trace a row from insertion through a crash before send, each scheduled failure, a later success, and terminal exhaustion. Check that the scheduler reads pending rows independently of the original creation window, that the source and recipient are still eligible before each attempt, and that every actual transport call has an audit entry. Keep provider acceptance, inbox receipt, and an ambiguous SMTP result distinct; a repeated call can deliver twice when the first outcome is unknown.
- For a manual retry beside a capped worker, compare the retry endpoint's update predicate with the worker's claim predicate at the exact attempt limit. An API response that says "queued" must describe work the worker can still claim. Make exhausted work terminal in stored state and both operator screens, while preserving completed steps and a clear manual-review path.
- For an external or document requirement with two dated milestones, represent its allowed branches and the transition between them in the acceptance scenario. Capture evidence at each deadline; a generic checklist of available documents cannot prove that a later required registration, receipt, or approval happened on time.
- When two screens control the same decision, compare confirmation, required fields, success wording, and retry behavior on both screens even if they call one API. Shared server code does not guarantee the same user-facing rule.
- For static help that describes a conditional integration, compare each supported navigation branch with the actual destination, tab behavior and provider-specific steps. Phrase instructions by the routing condition rather than assuming one provider name implies one route.
- When a screen chooses an action from an event's mode or type, trace that discriminator from stored record through every API projection and response schema to each consuming screen. Check that a canonical record with no legacy URL or profile still exposes the action, and that each action reaches an authorized endpoint.
- For files and external media, verify the bytes endpoint as well as the page that lists the item. Check whether a saved URL remains usable after unpublishing, expiry, role change, or removal from an audience; list filtering alone does not revoke a direct link. Compare upload permission, reference binding, content read, deletion, and cleanup separately.
- Before allowing deletion of a stored file, compare the delete guard with every persisted file ID and legacy URL field in the relevant schemas, including nested arrays. Reuse the reference predicate in retention cleanup; if a required model is unavailable, do not treat that absence as proof that the file is free.
- For deletion across object storage and a database row, inspect the actual order, preview or derivative objects, partial batch errors, response contract, and retry after either store fails. Keep the row until storage deletion succeeds; make repeated object deletion safe if the final database write fails.
- For personal-data erasure that anonymizes a profile before deleting its files, snapshot the exact file IDs in the confirmed operation while the links still exist. Check shared references before deleting bytes, retry after a partial storage failure, and fail closed for an older operation whose required snapshot is missing. Treat a staff-entered external receipt as an auditable assertion: record its source reference, confirmation time and actor, gate completion on local steps, and say explicitly whether the external service was independently checked.
- For a storage migration that invalidates old object URLs, inventory URLs stored outside the file row. Copy and verify the original and derivatives before switching reads, rewrite supported embedded URLs before deleting old bytes, and persist enough progress to retry cleanup. Block records whose viewers still depend on a direct URL; distinguish an unpublished migration script from migrated live data.
- When a private file is attached to a protected record, compare the record action/read capability with the direct file-read predicate. Assignment to a course or group may grant ordinary learning access without granting the stronger right to read exclusion, discipline, personnel or other protected evidence.
- For anonymous answers with file uploads, check the uploader at attachment time, the storage bucket, direct file access, deletion references, filename and uploader metadata, and the viewer path. The file content itself can identify its author; show that limit to the uploader instead of claiming complete anonymity from metadata redaction.
- For audio or video accessibility, distinguish an unsynchronized transcript below the player from timed captions that a viewer can turn on over the media. Check stored cue timing, the authoring or provider source, learner playback, and each media type covered by the requirement.
- For a digital trace produced from browser telemetry, identify which values the client asserts and which the server independently verifies. Check numeric consistency, access, monotonic updates and event emission with a direct request; label a client report as such until the required evidence standard is agreed.
- For a feature promised on a generic recording, compare every supported source type (managed stream, external URL and uploaded file) with the editor, API access predicate and viewer. If only one source has captions, corrections or navigation, state that boundary in the requirement and user flow before claiming the generic feature is ready.
